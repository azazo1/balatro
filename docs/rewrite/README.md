# Rust 重写

用 Rust 重写原版 Balatro 的规则层, 目标是给批量跑基准与分析用: 没有界面, 不依赖 LOVE 与图形环境,
每一步都能存快照与回滚, 可以并行跑很多局. 只覆盖原版内容, 不含 mod.

代码在仓库根的 `engine/`, 是一个零依赖的 crate.

## 为什么不是"把逻辑抽出来"

游戏里规则与界面是交织的, 抽不出一个干净的核心:

- 出牌的入口是 `UIBox:get_UIE_by_ID("play_button", ...)` 拿到按钮再调 `G.FUNCS.play_cards_from_highlighted`.
- 出牌逻辑内部按渲染坐标排序: `table.sort(G.hand.highlighted, function(a,b) return a.T.x < b.T.x end)`.
- 逻辑分支里直接操作界面对象: `G.HUD_blind:get_UIE_by_ID('HUD_blind_debuff_1'):juice_up(0.3, 0)`.
- 选中一张小丑会创建界面对象 (`Card:highlight` 里建 `use_button`).

所以只能重写. 好在规则本身是可读的, 并且有足够的对照物.

## 验证方式

重写最大的风险是"看起来能跑但与原游戏不一致", 所以每一步都要对拍, 不靠推理:

| 层 | 基准来源 |
| --- | --- |
| 随机数 | 本机 LuaJIT 直接生成序列, 见 `engine/tests/lua/dump_rng.lua` |
| 开局发牌 | `recordings/` 下各局的 `.replay.json` 里每一步的 digest |
| 牌型判定 | `docs/game/rules/poker-hands.md` 的规则与基础值表 |
| 计分 | `bbdump` 导出的每步完整状态 (含 `round.chips` 与 `round.last_hand`) |

`digest` 是游戏自己算出来的状态摘要 (state / ante / round / money / 牌堆张数 / 各区域牌列表 / 待办目标),
每一步都有, 所以任何实现只要能逐步复现它, 就说明那一层对上了. 但它不含分数.

**分数真值**由本仓库新增的 `bbdump` mod 产出. 它只订阅 bbcore 的活动事件
(`BB_ACTIVITY` 的 `response`), 不拦不改任何请求或响应, 也不依赖 bbreplay: 外部 HTTP 调用, 内置 loop
的本地调用与游戏内回放都经过那个事件, 所以三种玩法都录得到, 输出也不写进 `.replay.json`.
已在 2026-10-04 实机验证可用.

```shell
BBDUMP=1 BBDUMP_DIR="$PWD/recordings/dumps" just macos run-agent
```

一局一份 `<启动时间>.dump.jsonl`, 一行一次动作, 默认目录 `<存档目录>/dumps`, 用 `BBDUMP_DIR` 改.
每行除了状态还带**这次请求的参数**与 `seed` / `deck` / `stake` —— 没有它们就无法复盘: `response`
事件本身不带参数, 所以 `bbdump` 额外订阅了 `BB_ACTIVITY` 的 `call` 事件把参数先存下来.
同目录下还有 `bbdump-trace.log`, 记 mod 是否加载, 钩子是否被调用与出错原因 —— 它**不看 `BBDUMP`**
就写, 因为"环境变量没传到游戏进程"与"mod 没加载"是两回事, 只看 dump 文件区分不出来.
详细说明见 [mods/bbdump/main.lua](../mods/bbdump/main.lua) 的文件头.

## 可复现性的两处前提

`b3ff12a` (待办清单) 与 `8eb8c9c` (轨道标签) 是两个 breaking fix, 都改了 `game/` 下的代码.
在那之前的回放里这两处的随机性无法复现, 所以:

- 基准数据只取这两个 commit 之后的对局 (例如 ALEEB 那 12 局, 记为 `1.0.1o+71c8f71`).
- 实现跟随**当前**的 `game/` 代码, 不是上游原样.

## 进度

已完成并通过对拍:

- `rng/`: LuaJIT 的 `math.random` (TW223 加 `random_seed`) 与游戏的 `pseudoseed` 状态机.
- `cards/`: 牌的表示, 建牌顺序 (`sort_id`), 手牌排序 (`get_nominal`).
- 开局链路: 两次洗牌 (`shuffle` 与 `nr1`) 加发牌, 与 ALEEB 的第一条 digest 一致.
- `scoring/poker_hand.rs`: 12 种牌型的判定, 含四指, 捷径, A 两端, 包含回填, 石头牌, 万能牌, 模糊小丑.
- `scoring/hand_levels.rs`: 牌型的等级与基础值.
- `data/`: `catalog.json` 的解析 (自带一个极简 JSON 解析器, 不引第三方依赖).
- `run/`: 候选池, 抽取与商店货架. 已对拍种子 ALEEB 的第一个商店整条:
  `shop=j_trading!e,j_rocket vouchers=v_magic_trick packs=p_buffoon_normal_1,p_arcana_normal_4`.
  连永恒修饰 (`!e`) 与"首次进店必给基础小丑包"的特例都一致.
- `run/snapshot.rs`: 每步快照与回滚. 回滚后重跑同一条路, 结果与没走过岔路的局一致; 同一份快照
  可以反复取用, 这是分支探索的基础.
- `scoring/engine.rs`: 一次出牌的计分 (暂时不含小丑与增强). 已对拍 ALEEB 的第一手:
  顺子 70 筹码 × 4 倍率, 等离子平衡成 37 × 37 = 1369.
- `jokers/`: 小丑的触发框架, 已接 `before` (成长), 逐卡 (`individual`), `joker_main` (回收) 与
  `after` (融化/掉次数) 四个阶段. 已实机对拍过 `j_joker`, `j_jolly`, `j_sly`, `j_zany`, `j_wily`
  五张的总分 (324 / 400 / 1681 / 1369 / 6561) 与备用裤子打出两对的 676. 另有十张按规格实现并由
  测试覆盖: 绿色小丑, 方形小丑, 跑步选手, 搭乘巴士, 冰淇淋, 汽水, 卡尼奥, 笑脸, 奇数托德,
  以及条件不命中的那批. `after` 阶段还会报告"用完就没了"的小丑 (冰淇淋融化), 由调用方移出持有区.
  逐卡那一步的粒度要注意: 笑脸对**每一张**人头牌各给一份倍率, 不是整手给一次.
- 又补了八张: 四张**花色小丑** (贪婪 / 色欲 / 愤怒 / 暴食, 每张该花色的计分牌给 +3 倍率,
  走逐卡那一步, 四张共用同一段实现, 差别只在原型里的 `extra.suit`), 以及四张**看局面**的
  (旗帜看剩余弃牌给筹码, 神秘之峰看弃牌清零给倍率, 斗牛按现金给筹码, 抽象小丑按持有张数
  给倍率 —— 它**把自己也算一份**).
  为此 `EvalEnv` 多了 `discards_left` 与 `dollars` 两项, `play` 在算分前把当前值填进去;
  计分本身仍然不碰局面, 值都是传进来的.
- 再补七张: 斐波那契 (A/2/3/5/8 给倍率), 恐怖面孔 (人头牌给筹码), 偶数史蒂文 (偶数点给倍率),
  学者 (A 给筹码与倍率), 对讲机 (10 与 4 给筹码与倍率) 走逐卡; 钢铁小丑 (手里每张钢铁牌让倍率
  乘 1.2) 与蓝色小丑 (牌堆每张给筹码) 走主效果, 为此 `EvalEnv` 又多了 `deck_len`.
- **顺手修掉一个真 bug**: 主效果里那段"成长出来的筹码"原本**无条件**把 `extra.chips` 加进去,
  而学者与对讲机的 `extra` 正好也是 `{chips, mult}` 这个形状 —— 那是"给特定牌的固定值",
  于是学者给**每张牌**都加了 20 筹码. 修法是只让真正把它当成长值的那三张
  (方形小丑 / 跑步选手 / 冰淇淋) 走那段. 教训是**同一个字段形状在不同卡上语义不同**,
  按形状判断会误伤.
- 又补了五张**回合末给钱**的 (黄金小丑 / 9 霄云外 / 火箭 / 卫星 / 延迟满足), 对应
  `Card:calculate_dollar_bonus`. 它们与"计分时给钱"是两回事 —— 不看这一手打了什么, 只看局面,
  所以那笔钱算进结算栏的 `card_bonus`, 与黄金牌金封同一个口袋. 为此 `EvalEnv` 与
  `TriggerContext` 又多了 `deck_nines` / `planets_used` / `discards_used`, 而 `RunState` 记下了
  `planets_used` (用行星牌时加一).
- 积分卡也做了: 拿到之后每打六手给一次 x4, 落在第 5 / 11 / 17 ... 手上. 游戏那边的算式是
  `(4 - n) % 6 == 5`, 而 Lua 的取模结果跟模数同号, 化简下来就是 `n % 6 == 5` ——
  两个方向都容易看错, 所以测试把前十一手逐手数了一遍, 该给的给, 不该给的不给.
  为此 `Joker` 多了 `hands_since_gained`, 在 `before` 阶段加一.
- 方尖碑也做了: 打的是"本局**唯一最多**的牌型"时重置成 1, 否则涨 0.2. 判定里用的是 `>=`
  而不是 `>`, 所以**并列时算增长** —— 这一点最容易看反, 测试用"对子与同花都打过三次"那种
  并列局面把它钉住了.
- **顺手修掉第二个真 bug**: `Joker` 的乘倍率原本按小写 `x_mult` 去读原型, 而原版里那一项
  写作 **`Xmult`** —— 全库 13 张用它的牌 (星座 / 吸血鬼 / 全息 / 方尖碑 / 幸运猫 / 拉面 ……)
  于是全都读成 0, 也就是**乘倍率一直没生效**. 按大小写读错这种事编译器不会提醒,
  只能靠"拿一张真牌跑出数来"发现.
- 修完那个字段名之后做了一次**字段审计**: 把引擎读的十来个字段名与原型的实际字段对照了一遍.
  结论是除 `Xmult` 之外没有第二处读错. 顺带发现四张改**回合次数**的小丑 (杂耍师: 手牌 +1,
  醉汉: 弃牌 +1, 快乐安迪: 弃牌 +3 手牌 -1), 它们与信用卡同类 —— 进场生效、卖掉撤销,
  所以抽成了一对 `apply_joker_on_gain` / `apply_joker_on_loss`, 两边的 `match` 必须一样.
- "牌型匹配才乘倍率"的那批 (二重奏 / 三重奏 / 一家人 / 秩序 / 部落) 本来就工作,
  只要 `Xmult` 读对 —— 测试顺带把这一类也验到了.
- 审计还发现三张**生成牌**的塔罗没做, 一并补上: **女祭司** (给行星牌), **皇帝** (给塔罗),
  **审判** (给小丑). 它们的张数受消耗槽空位限制, 而游戏那边的循环次数是
  `min(给的张数, 上限 - 开始时的张数)` —— "开始时的张数"**含原牌本身**, 所以默认两格上限下
  用一张塔罗只给得出一张. 想要两张得先腾出位置, 测试把三种槽位情况都覆盖了.
- **幻灵牌**开始接了 (原版 18 张): 加蜡封的四张 (护身符 / 既视感 / 入迷 / 灵媒), 神秘生物
  (复制第一张选中的牌, 手牌因此变多), 符印 (整手牌换成同一个**随机**花色), 占卜
  (整手牌点数**统一**成一个随机点数, 且**手牌上限减一**).
  **占卜的名字很误导** —— 听起来像"点数降一级", 看源码才知道是统一. 这一类"名字与效果不符"
  的地方已经遇到好几次了, 只能靠读源码.
  还差的幻灵多是生成牌的 (使魔 / 严峻 / 咒语 / 火祭 那批要销毁随机手牌再补新牌)
  与改小丑的 (生命十字章 / 妖法 / 灵质).
- 又补了"销毁一张再补新牌"的四张: 使魔 (补人头牌) / 严峻 (补 A) / 咒语 (补数字牌) /
  火祭 (删五张换二十块). 销毁的那张是**彻底删掉**, 不进弃牌堆 —— 所以整副牌真的会变少,
  后面的洗牌跟着变; 补的牌点数与花色各有各的随机键 (`familiar_create` 那种).
  同一张牌的**点数与花色用的是同一个键**, 靠 `pseudoseed` 递推拿到两个不同的值.
  还差的幻灵是改小丑的那三张 (生命十字章 / 妖法 / 灵质).
- 那三张也做了: **生命十字章** (随机留一张小丑并复制一份, 其余非永恒的删掉 ——
  永恒的**删不掉**, 所以它们总是留下), **妖法**与**灵质** (从"还没有版本"的小丑里挑一个,
  分别加多彩与负片; 一个都没有就什么也不做). 为此 `Joker` 多了 `edition` 与 `eternal` 两项.
  这几张的挑选用 `pseudorandom_element` 的做法, 挑中的下标要按"可选池"算而不是按全部.
  幻灵 18 张里还差四张: 光环 (给手牌加闪箔/镭射/多彩), 幽灵 (生成稀有 小丑),
  灵魂 (生成传奇小丑) 与黑洞 (升级全部牌型).
- 那四张也做了, **幻灵 18 张至此全接完**. 光环用的是 `poll_edition` 的"必定出版本"那一档
  (阈值乘 25), 所以不会空手而归. 幽灵给稀有, 灵魂给传奇, 黑洞给所有牌型各升一级.
  做这一批时踩到两个**池子上的规则**:
  1. **传奇 (4 级) 无视解锁条件** —— 池子的过滤写作 `(v.unlocked ~= false or v.rarity == 4)`.
     少了这一条, 传奇池永远是空的, 灵魂就变成"用了没反应".
  2. **传奇的池键不带底注** (源码里是 `not _legendary and ante or ''`), 其余带.
  另外给 `pick_or_resample` 加了保护: 池子里一张可用的都没有时直接返回占位而不是继续重抽样,
  否则会**无限循环** —— 这正是传奇池为空时发生的事.
- 顺着那次无限循环做了一次**循环审计**: 引擎里只有两处重抽样循环, 而它们本是同一件事却写了两遍
  —— 一处加了保护另一处没有. 现在合并成一份实现, 以后不会再出现"某个入口卡死".
- 审计池子的过滤时又发现漏了一条: 池子写作
  `not (used_jokers[v.key] and not find_joker("Showman"))`, 即**持有表演者时用过的小丑还能再出现**.
  少了这条例外, 表演者就成了没用的小丑.
  顺便记一个坑: **表演者的原型键是 `j_ring_master`**, 与它的名字 `Showman` 完全不同 ——
  这类"id 与名字不符"的地方已经遇到好几次, 写之前先去 catalog 查确切 id 比让编译器/测试告诉你要省事.
- 顺着这条线索又查了一遍**重复实现**: "按稀有度抽小丑"这件事在引擎里有**三份**手抄版
  (商店货架 / 标签强行指定 / 幻灵的幽灵与灵魂), 而它们的过滤条件已经悄悄不一致了 ——
  一份漏了表演者的例外, 另一份漏了传奇免解锁. 现在合成一个 `pick_joker_of_rarity`,
  三处都走它.
  **"同一个逻辑抄三遍"本身不是错, 错在抄完之后三份会各自漂移**; 而这三次漂移都是我这些轮
  陆续修 bug 时留下的 —— 每次只修了眼前那处.
- `cards/` 的强化牌在计分时的效果: 奖励牌与石头牌给筹码 (30 / 50), 倍率牌给倍率 (4),
  玻璃牌乘倍率 (2), **钢铁牌乘倍率 (1.5) 但只在留在手里时算**. 这几份数值都**从强化现取**
  而不是另存字段 —— 换强化时就不会忘记同步 (踩过一次: `set_enhancement` 只改了标签,
  结果奖励牌不给筹码).
  玻璃牌的乘倍率作用在"当前已攒起来的倍率"上, 所以它放在哪张牌、前后还有哪些倍率来源,
  结果都不同, 测试用同一副同花钉住了这一点.
  钢铁牌要一个**独立的阶段**: 计分流程是"逐卡计分 -> 手牌 -> 小丑主效果"
  (`state_events.lua` 的 582 / 798 / 905 三段), 手牌那一段遍历的是**没打出去的牌**.
  所以 `score_play_with_held` 单独一个入口, 不需要它的调用点仍然用 `score_play`.
  幸运牌 (要掷骰) 与黄金牌 (回合末结算) 还没做.
- **幸运牌**是唯一需要随机数的计分: 两次独立掷骰 (`lucky_mult` 1/5 给 +20 倍率,
  `lucky_money` 1/15 给 20 块). 骰子**由调用方在计分之前掷好**再填进 `HandCard`, 这样
  `score_play` 保持纯函数, 掷骰顺序也由调用方掌握 —— 游戏里是先倍率后钱
  (`eval_card` 里 `get_chip_mult` 在 `get_p_dollars` 前面), 顺序换掉随机数就对不上.
- 蜡封的钱有**两条不同的路**, 别合并: **金封是在打出去那一刻给三块** (走 `get_p_dollars`,
  计分阶段), 而**黄金牌是留在手里到回合末才给** (走 `get_end_of_round_effect`, 算进结算栏).
  一开始我把两个都放在回合末, 结果带金封的牌只要不出手就一直给钱.
  红封也在计分那条路上: 它让这张牌**整段重跑一遍** —— 不只是筹码加倍, 逐卡小丑 (笑脸那种)
  也跟着再算一次, 所以两件事要一起验. 蓝封在回合末给一张"最后打出牌型"对应的行星牌
  (消耗槽有空位时), 所以 `RunState` 记了 `last_hand_played`. **紫封在弃牌时**给一张塔罗,
  也是消耗槽有空位才给.
- 看**留在手里**的牌的小丑: 男爵 (手里每张 K 给 x1.5), 射月 (每张 Q 给 +13 倍率),
  致胜之拳 (只给点数最小的那张, 值是其点数的两倍). 前两张按 `other_card` 判, 第三张要看到
  **整手**才知道谁最小 —— 所以 `Joker::held` 的签名带着全部手牌. 同点数时游戏留下的是靠左那张,
  石头牌不参与比较.
- `cards/` 与 `run/` 的消耗牌部分: 塔罗已做十五张, 行星十二张也全做了 (升对应牌型一级).
  塔罗覆盖 `card.lua` 里的效果分支 ——

  (点数 2/3/4/5 的牌多算一遍), **黄昏** (最后一手里每张都多算一遍), **挂账**
  (只有第一张计分牌多算 —— 原型里 `extra` 是 **2**, 也就是多算两遍), **汽水** (每张都多算一遍).

  但**从来没有人读** —— 也就是说汽水一直是个空操作. 现在把那个字段删了 (留着只会误导),
  换成 `Joker::retrigger` 这个真正的阶段.
- 顺着这条线做了一次**"只写不读"审计** (把所有结构与上下文里的字段列出来, 看有谁读),
  又挖出四处**静默缺口** —— 它们的共同点是"赋值写得漂漂亮亮, 但从来没有人消费":
  1. `ScoreResult.melted` 由计分那一层产出, 但 `play` **从来没消费它** ——
     也就是说**冰淇淋与汽水永远不会离开队伍**. 现在在算分之后按 `melted` 把下标从后往前删.
  2. `TriggerContext.held_len` 只写不读 (早期按"张数"看手牌的遗留), 删掉.
  3. 商店给租赁小丑打的 `rental` 标记**买下之后没人管** —— 租金从来没扣过.
     现在回合末每个租赁小丑扣三块 (`G.GAME.rental_rate`).
  4. 易腐小丑的 `perish_tally` 同样没人管 —— 从来不过期. 现在回合末倒数, 到零就**变成被削弱**.

  这一轮的利息. 顺序是从源码里核出来的 (`calculate_rental` 在第 108 行, 利息在第 1191 行),
  不是随手放的.

  削弱本来就是一(张)小丑一个状态 (易腐到期只关掉那一张, 绯红之心也只关一张),
  放在上下文里等于全队一起停.
- 审计时又发现**包里的牌少了一大截东西**: 商店货架上的小丑会掷"永恒 / 易腐 / 租赁 / 版本"
  这四样, 而**包里的小丑一样都没掷** —— 而且 `PackCard` 里连装这些标记的字段都没有,
  所以就算掷了也带不到手里那张上.
  游戏里这两处的**键不一样**: 商店用 `etperpoll` / `ssjr`, 包里用 **`packetper` / `packssjr`**
  (版本那一项两边共用 `edi`). 也就是说"同一个特性"在两条路上是两套键 ——
  **少掷一次不只是那张牌少了特性, 后面的随机序列还会整体偏掉**, 这一点比缺个标记更严重.
  现在包里的小丑按同样的顺序掷三下, 取出来时把四个标记一起带过去.
- 又换了个角度审计: 把**游戏源码里所有随机数的键**列出来 (37 个), 与引擎用到的对比.
  16 个没对上, 其中大部分属于**还没做的小丑** (8 球 / 血石 / 生意 / 空间 / 疯狂 / 隐形 /

  1. **使魔 / 严峻 / 咒语造出来的牌要带一个随机强化** (键 `spe_card`, 池子是全部强化去掉石头牌).

  2. **严峻的掷骰次数是错的**: 游戏里严峻的点数固定是 A, **只掷花色一次**;
     我多写了一个"空掷", 于是花色取到了 `grim_create` 那条链上的**第二个**值.
     这一条比"少了特性"更麻烦 —— 它是**随机数序列错位**, 而不是缺个东西.

- **把骰子交给计分那一层** (这是本轮最大的改动). 以前"每张计分牌掷一次"的效果只能靠调用方
  预掷好再传进来 (幸运牌就是这么干的), 可这种做法遇到"队里有几张就掷几次"就撑不住 ——
  计分那一层得知道"这一次掷的是哪张小丑的", 而它只知道牌.
  现在多了一个 `score_play_with_rng`, 把 `&mut Rng` 一路带到逐卡阶段; 原来的
  `score_play` / `score_play_with_held` 保留原签名 (内部用一个固定种子的临时骰子),
  所以**一百多处调用点一处都没动**, 真正的对局走带骰子那个入口.
  于是补上两张一直在等这个的: **血石** (每张红桃掷 1/2, 中了乘 1.5) 与 **生意**
  (每张人头牌掷 1/2, 中了给两块). 顺带删掉了幸运牌那两个"预掷结果"字段 ——
  留着它们就会变成下一处"只写不读".
  这一改又带出**两个真问题**:
  1. 原来的预掷给**所有打出的牌**都掷了骰, 而游戏只给**参与计分**的牌掷 ——
     也就是打五张牌只有两张成对时, 会多掷三次, 随机序列直接偏掉.
  2. **`play` 从来没把手牌交给计分** —— 也就是说钢铁牌与男爵 / 射月 / 致胜之拳
     那几张"看手里剩下的牌"的效果, **在真实对局里从来没生效过**.
     机制做得好好的, 也单独测过, 就是没接到对局那条路上. 这类缺口比"算错"更隐蔽:
     计分函数本身没问题, 测试也过, 只有真打一局才看得出少了一截.
- 第 100 轮又换了个查法: **让每张小丑都跑一遍场景, 看它到底会不会改变结果**.

## 实机验证

光对回放文件不够: 回放只覆盖它录过的局面, 想验某张小丑在某个牌型上的行为时很难凑巧录到.
真游戏能直接用 `add` 端点塞卡牌, 所以可以精确构造局面:

```shell
just agent-call add '{"key":"j_jolly"}'     # 塞一张小丑
just agent-call add '{"key":"S_T"}'         # 塞一张扑克牌
just agent-call play '{"cards":[0,1]}'      # 打指定的牌
just agent-call gamestate | jq '.result.round.last_hand.text'
```

`last_hand.text` 是那一手的计分明细, 逐行写着每个来源加了多少, 例如:

```text
梅花10 | +10 筹码 | 20x2
方片10 | +10 筹码 | 30x2
Jolly Joker | +8 倍率 | 30x10
= 400
```

这比回放给的信息细得多 —— 回放只有一步一个摘要, 而这里能直接看到**小丑排在计分牌之后**,
以及等离子平衡发生在所有小丑之后.

## 待查

- **批量并行跑对局**已经做了, 见 `src/batch/`: 引擎里没有全局可变状态 (原型表只读, 一局的全部
  状态都在 `RunState` 里), 所以并行只需把种子分给几个线程, 不用锁也不用重建什么.

## 实现时容易踩的坑

从 `Card:calculate_joker` 的规格整理里挑出来的几处:

- 石头小丑, 钢铁小丑, 驾驶执照的计数在 `Card:update` (L4179-4202) **每帧重算**. 引擎没有帧循环,
  这些要改成按需从牌堆现值计算.
- 待办清单的目标牌型在 `Card:set_ability` (L311-323) 抽取, 且保证与上一次不同.
- 加钱有两种写法: 多数小丑只设 `dollars` 并动 `dollar_buffer`, 待办清单与斗牛士另外直接调 `ease_dollars`.
- 花盆与重影对万能牌各有一次额外扫描, `is_suit` 传参不同, 花色判定顺序也不同.
- `context.cards_destroyed` 在本仓库全部 Lua 里**没有任何派发方**, 是不可达分支; 真正生效的是
  `context.remove_playing_cards`. 卡尼奥与玻璃小丑各有两份实现, 语义还不一样.
- 蓝图 / 头脑风暴能不能复制某个小丑, **不看 `blueprint_compat`** (那是纯界面字段), 只看代码里
  有没有 `not context.blueprint`. 所以需要按小丑逐个核对该守卫.
- 疯狂在可销毁目标列表为空时**不消耗随机数** (`#list > 0 and pseudorandom_element(...) or nil` 短路),
  这种短路会改变后续的随机序列.
- 抽到占位后的重抽序号是**从 2 开始**的: `it = 1` 之后进循环先自增, 用的是 `_resample2`. 写成
  `_resample1` 会悄悄换掉整条随机序列 (这个坑已经踩过一次, 见 `run/pool.rs` 的注释).
- `modifiers.no_blind_reward` 在赌注 2 起只设了 `Small = true`, 取消的是**小盲注**那份固定奖金,
  大盲注 ($4) 与 Boss ($5) 照发. 当成"所有盲注都清零"就会让 Boss 的收益少 $5 (这个坑也踩过).
- 回合计数 `round` 是**全局限次**, 不随底注重置: 底注 2 的小盲注是 `round=4` 而不是回到 1.

- 顺着"终局 Boss"这条线查下去, 先是一个**虚惊**: 按名字搜 `bl_final_*` 得到 0 次出现,
  但它们其实是**数据驱动**的 —— 目录里本来就有这五条 Blind 记录, 池子照样取得到.
  于是写了个探针去底注 8 抽一次, 结果探针**直接报错**: **"第 8 底没有可用的 Boss"** ——
  这是个会让整局崩掉的真 bug (对"可批量跑对局"来说很致命).
  根因: 游戏那边 `get_new_boss` 是两支**并列**判断 —— 普通 Boss 看 `min <= 底注`,
  而终局 Boss (`showdown`) **只看"底注是不是 `win_ante` (8) 的倍数"**, 不看 min/max.
  引擎把两支都塞进了同一个 `boss_reachable` (查 min), 而终局那五条的 `min` 是 **10** ⇒
  底注 8 时一个候选都没有. 改成分支判断之后底注 8 能抽出 `bl_final_acorn`, 并补了测试
  (底注 8 出 showdown, 底注 4 出普通).
  这五条的**效果**还没做 (翠叶的"所有牌失效直到卖掉一张小丑"之类), 记在待办里.

- 上一轮那个"底注 8 抽不出 Boss"的 bug 说明**高底注的路径基本没被跑过** (短对局到不了那儿),
  所以做了一次**深度烟测**: 把每一底的目标分压到 1 分 (只为走遍流程, 不为打得好看),
  让一条对局一路推下去 —— 结果从底注 1 走到**底注 34** (400 步) **没有崩**.
  这条路覆盖了 8 / 16 / 24 / 32 四个决战底、高底注的商店、包与各种结算,
  也就是说那个崩溃点是这条路上唯一的坑 (至少目前是).
  把它转成了常驻测试 (`a_long_run_survives_many_antes`), 与"一百条短对局"那条互补:
  那条铺**广度** (一百个种子各跑几步), 这条钻**深度** (一条对局跑到三十多个底).
  两条烟测的取向不同, 单靠任一条都会漏掉另一类问题.

- 把那五个决战 Boss 的**效果**做了三个 (选谁早就在跑, 缺的是它们各自做了什么):
  - **琥珀橡果** (`bl_final_acorn`): 开局把小丑的顺序**洗三次** (键 `aajk`). 小丑的先后会影响计分
    (先算谁、谁给谁加成), 所以这不是"看不见的效果".
  - **翠叶** (`bl_final_leaf`): **所有扑克牌**失效, 小丑不受影响; **卖掉一张小丑**就把这个盲注
    整条关掉 (用的是与奇可同一个 `disabled` 开关).
  - **猩红之心** (`bl_final_heart`): **每次发牌**先把所有小丑恢复, 再挑**一个**随机的让它失效
    (键 `crimson_heart`).
  还剩两个: **蓝铃** (强行锁定一张牌不能取消选中 —— 那是个"能不能这么出牌"的约束) 与
  **紫瓶** (只是盲注倍率 ×6, 这条本来就走通用的 `blind_multiplier`, 不用单独写).
  这三条原来都是**静默无效**的: 到了决战底照打, 只是 Boss 什么也不做.

- 最后那个有实际效果的决战 Boss 也补了: **蓝铃** (`bl_final_bell`) —— 每次发牌锁住手里的一张,
  那张**不能取消选中**, 所以每次出牌都得带上它.
  做法与游戏一致: 在牌上打一个 `forced_selection` 标记 (游戏的 `card.ability.forced_selection`),
  "手上还没有被锁的牌"时随机锁一张 (键 `cerulean_bell`), 出牌时把带标记的自动带上.
- 这处又踩了一次**时机**的坑, 而且是测试抓到的: 我一开始把"锁一张"放在 `draw_to_hand` 的**开头** ——
  那时手牌还是空的, 于是**永远不锁**. 游戏的钩子叫 `drawn_to_hand`, 本身就是"发完之后"那一趟.
  挪到函数末尾就好了. 这类错与之前几处 (尤里克先判后减、小不点先付账后成长、隐形小丑先移除后判断)
  是同一个形态: **放错了时机, 而编译器不会提醒**.
- 至此五个决战 Boss (琥珀橡果 / 翠叶 / 猩红之心 / 蓝铃 / 紫瓶) 的效果都有了 ——
  紫瓶本来就只是盲注倍率 ×6, 走通用的 `blind_multiplier`, 不用单独写.

- 那个"放错时机"的错犯到第四次之后, 做了一次**时机清单**的审计: 把游戏 `calculate_joker` 里
  所有的 `context.*` (二十来个) 列出来, 逐个问"引擎在哪儿做这件事".
  结论是主要那几个 (before / joker_main / individual / held / other_joker / repetition /
  after / end_of_round / discard / selling_card / ending_shop / first_hand_drawn) 都有对应,
  缺的是几处**边角时机**: `using_consumeable` / `skip_blind` / `reroll_shop` / `open_booster` /
  `cards_destroyed` / `buying_card` / `debuffed_hand` / `remove_playing_cards`.
- 接着按稀有度全扫了一遍"既没按名字实现、配置也不走通用分支"的小丑, 得到 **36 张**
  (普通 13 + 罕见 23; 稀有与传奇这两档是零). 这份名单是**候选**不是结论 ——
  有些其实在别处实现了 (例如 `j_four_fingers` / `j_smeared` 是牌型判定参数, 走 `EvalEnv`).
  本轮从里面挑了最容易核实的两张:
  - **混沌小丑** (`j_chaos`): **每回合**多一次免费重抽. 注意它不是"拿到时给一次" ——
    游戏是在每回合开始那一趟加, 而 `current_round` 每回合重置. 顺手发现引擎里
    `free_rerolls` 这个计数**从来没被重置过** (又一处"只读不重置"), 一并补上.
  - **蛋** (`j_egg`): 每过一个回合自己的**卖出价**涨 3 块. 为此给 `Joker` 加了

  共同点都是: 引擎对、断言错.

- 又补了一张**待办清单** (`j_todo_list`): 打出的牌型正好是它这一回合指定的那个, 就给 4 块并**换一个**.
  这张有两处值得记:
  1. 换牌型时游戏写的是 **`while not to_do_poker_hand`** —— 也就是"循环掷到和原来不同为止",
     而**每次掷都推进 `to_do` 这个键**. 省成"掷一次"就会少推一次, 后面所有按键取随机数的地方

- 这四张里有两张是"改一条已有规则"(利息率 / 卖价), 两张是"复用已有的开关"(禁用盲注 / 免费判定).

- 写测试时又简化了一次: 一开始想"从弃牌堆里挑出刚才打的那几张"再逐个断言, 但那要先认得出来是哪几张

- 卡了很久的那个"开包时那 8 张手牌从哪来"查清了, 而且当初的结论(四种机制都试过, 对不上)
  之所以一直对不上, 是因为**问题根本不在那 8 张牌的算法上**: 它们就是"从牌堆顶补一手牌"
  这个最朴素的做法, 而当时牌堆**顺序**本身就与游戏不同. 于是这一步的修法不是去凑那 8 张,
  而是把上游几处顺序问题都改对, 它自己就好了. 具体是四件事:
  - **结算屏那一下会洗牌** (`G.FUNCS.cash_out` 开头那句 `G.deck:shuffle('cashout'..底注)`).
    它对牌堆的**顺序**是隐形的 (洗牌前总会按 `sort_id` 排一遍, 所以洗几次都一样), 但它决定
    店里开包时抽到的是哪 8 张 —— 因为补手牌那一步发生在两次洗牌**之间**.
  - **发手牌的是秘术包与幽灵包, 不是"凡是装消耗牌的包"**. 这条直接写在游戏里: 那两条开包路径
    各有一句 `G.FUNCS.draw_from_deck_to_hand()`, 而天体包那条没有 (Steamodded 那侧对应的开关
    `Booster.draw_hand` 也只给这两类置成 `true`). 我原来按"装消耗牌就发"判, 于是商店里每开一次
    天体包就凭空多一手牌.
  - **取包的顺序**: "把牌从包里拿出来 -> 立刻用在手牌上 -> 用完再看包取够没有". 关包会把整手牌
    收回牌堆, 而塔罗改的正是手牌 —— 所以先关包再用, 那两张牌就改不到. 这一处原来报的是
    "目标下标越界", 那是运气: 目标下标若恰好落在空手牌范围内, 它会安静地什么都不做.
  - **建牌序号 (`sort_id`) 有三处细节**, 每一处错了都表现成"发出来的牌不对", 而且都是静默的:
    新造的牌要有号且**单调递增** (不能写成"当前牌堆最大值加一", 那样一遇到"最大那张正拿在手里"
    就会发出一个偏小的号); 标准包里取出的牌要**插到牌堆底面** (游戏的 `emplace` 对牌堆是插数组
    头, 而取牌端在数组尾); 而**死神的复制不动目标的号**.

- 最后那一处值得单独记: 游戏那行是 `copy_card(rightmost, G.hand.highlighted[i])`, 第二个参数是
  **要写进哪张牌**. 给了它, `copy_card` 就走"复用这个对象"那一支, 只把牌面与能力写过去,
  `sort_id` 从头到尾没动; 而 DNA 与神秘生物那两处传的是 `nil`, 才真的新建一张牌、才吃掉一个新号.
  两种写法在 C 语言意义上只差一个参数, 在语义上是**相反**的. 我一开始把三处当成一类, 给死神的
  复制品发了新号 —— 那张牌的号于是从它在牌堆里的位置跳到最新, 排序后整副牌的顺序都变了,
  表现成"下一回合发出来的牌几乎全不对". 这类"两个调用长得很像、语义相反"的地方, 光看调用点是
  看不出来的, 必须翻到被调函数的**前两行**去看它怎么处理那个参数.

- 这一轮还补了一个**脚下那一层**的模块: `engine/src/lua/table_sort.rs`, 即 Lua 5.1 / LuaJIT 的
  `auxsort`. 缘由是手牌排序: 游戏的 `CardArea:sort('desc')` 用的是 Lua 的 `table.sort`, 而它
  **不稳定** —— 两张同点数的牌谁在前由快排的交换过程决定, 换成 Rust 的稳定排序就会给出不同的
  顺序, 而手牌顺序本身是状态 (出牌与弃牌用的都是下标). 这一处原来是 `sort_by` 直接顶上的.
  移植之后与真 LuaJIT 逐位对拍过 408 条.
  顺带查清了同一条线上的另一处: 两张**点数与当前花色都相同**的牌靠什么分先后 —— 靠

- 关于那份对拍数据, 有个教训值得写下来 (是**用户指出来的**): 它的初版每行只记了"值序列 -> 值序列",
  而**相等的元素在输出里长得一模一样** —— 三个 5 之间谁在前根本没有进输出, 所以那份数据只能验
  "排出来的值是对的", 换成任何一份稳定排序都会全过. 我当时还在注释里写着"值域开小是为了让相等

  黄色牌组少了十块钱. 现在按 [Back:apply_to_run](game/back.lua) 逐支对上, 分三步做:

  - **开局建堆之前** (`with_deck`): 各项数值. 券与起始消耗牌也在这一步, 但要记进
    `used_vouchers` **并施加效果** —— 只记不施加的话, 字谜牌组那三张券等于白送, 货架仍然按
    没买券的权重抽. 绿色牌组的"没有利息"跳过的是**整个利息**, 不只是那个"本金五块"的门槛,
    所以它成一笔开关 (`no_interest`) 而不是把利率设成零.
  - **建堆那一步** (`build_deck`): 无面牌组删掉 K/Q/J (于是 40 张), 错乱牌组把**每一次**
    都重掷成随机一张 (于是 52 张但会出现重复牌面), 棋盘牌组把梅花改黑桃 / 方块改红桃.
    顺序是固定的: 先"列出这副牌有哪些牌面", 再**按 `花色+点数` 字符串排序**, 最后换花色.
    第二步不是装饰 —— `sort_id` 是按排序后的名次分配的, 而它是洗牌前的定序依据.
    顺带把重复抽到的牌面各给一个新序号: 它们共用同一个原型, 照抄原型序号就会出现重号.
  - **开局那一次洗牌之前** (`apply_starting_deck_extras`): 券与消耗牌挂在 `E_MANAGER` 的事件上,
    而 `start_run` 自己也是个协程, 它在 `delay(0.5)` 处让出, 带 0.4 秒延迟的那一段就在这个缝里
    跑完, 之后才轮到 `G.deck:shuffle()`. 造消耗牌会掷一次版本, **动的是随机数序列**, 顺序反了
    整副牌的洗牌结果都会不同.

- 无尽模式这一轮的结论是**它在哪里结束**. 目标分数的算式是 `a*(b+(kc)^d)^c`, 指数增长,
  底注 38 还能表示 (`4.5e288`), 39 就超出双精度的 `1.797e308` 了 —— 于是游戏自己在 `nan` 上做
  `amount % magnitude` (`inf % inf`), 目标分数变成 `nan`. 而 `nan` 比大小永远是假,
  `chips >= blind.chips` 恒不成立, **那一底永远打不过**. 三个赌注档、小盲 / 大盲 / Boss 全都一样
  (倍率乘 `nan` 还是 `nan`).
  这个数是**用真 LuaJIT 逐位对拍过的**: 差一点就去"修"它了, 而修它就是引入偏离 ——
  引擎的职责是复刻, 不是替游戏收拾. 所以专门留了一份数据 ([dump_blind_amount.lua](engine/tests/lua/dump_blind_amount.lua),
  按十六进制浮点打印, 含成片的 `nan`), 谁想"顺手给个上限"都会在那里失败.

- 引擎遇上 `nan` 目标时的收场方式也验了: **干净地判负, 不崩, 也不"穿过"终点线**.
  这里我自己先写错过一条预期 —— 以为"出一次牌就该结束", 实际回合本来就该在"够了"或者
  "没次数了"时才收尾, 所以要打到手数为零. 后者才是危险的: 如果 `nan` 被误判成过关,
  对局会安静地跑到无穷远, 而统计上看起来像有人打通了 40 底.
  (顺带一提: 相同处境下游戏本体是有崩溃风险的 —— 它会把 `nan` 存进存档里的最高分,
  再拿它去比大小. 那是**存档 / 展示层**的问题, 与规则无关, 引擎里没有那一层, 所以不搬.)

- 引擎那边修了八处, 按性质分三类:

  1. **被拒绝的动作不该改状态** (两处). `buy` 把"从货架上拿掉"排在各项校验**之前**, 于是钱不够
     或持有区没位置时, 那一格照样没了; `take_and_use_from_pack` 在取牌失败时已经把可取的张数减了,
     而且会**把包关掉**. 两处都改成"先在副本上做, 成了才落到自己身上" —— 这比把校验一条条往前挪可靠,
     以后加一条校验也不会再错.
  2. **缺阶段检查** (两处). `cash_out` 在商店 / 输局之后照样返回成功; `next_round` 在包还开着时
     照样放行 (引擎会带着一个开着的包进下一个盲注). 游戏那边这两步都会拒绝, 而录像里正好都有
     这种重复尝试.
  3. **写漏的规则** (四处): 商店那个"买并使用"按钮整个没实现 (`buy_and_use`); 小丑入队时
     **没有给建牌序号**, 而洗小丑前要按它排序; 妖法 (`c_hex`) 该**销毁其余小丑**却只加了版本,
     顺带发现灵质每次**永久减手牌上限**且减得越来越多 (`ecto_minus` 1, 2, 3...), 而妖法/灵质的
     掷骰**键按牌分** (`hex` / `ectoplasm`, 不是共用一个 `wheel_of_fortune`); 取走包里的牌之后
     **没有从 `contents` 里删掉** —— 只有巨型包 (取完一次还开着) 才会露出来.
  4. 还有一处**行为差**: 手牌排序方式是**长期设置**. 游戏里那个按钮改的是 `G.hand.config.sort`,
     而 `draw_card` 结尾的 `to:sort()` 不带参数、沿用这个设置 —— 所以按过一次"按花色排"之后,
     **之后每次发牌**都照它排. 引擎原来永远按点数排. 顺带按 `get_nominal('suit')` 补上了
     **石头牌排到最后**那一条 (`mult = -1000`).

  还没有做, 记在下面的缺口里.

- 这一轮把验证的方向**反了过来**, 这也是 user 提的路子: 以前是"游戏怎么走, 引擎跟不跟得上"
  (引擎只能照着录像重放, 覆盖哪条路径全看录像里恰好有什么); 现在可以让**引擎先走并写下预测**,

- 为此把 digest 的生成与解析**从测试提进库** (`src/run/digest.rs`): 它是**与游戏之间的接口约定**
  (对着 `mods/bbreplay/replay/format.lua` 逐字写的: 卡片记号的顺序, 钱的写法, 区域顺序),
  生成器与对拍器都要用它. 留在测试里的话只能各写一份, 而两份只要有一处不一致, 对拍会整体报错
  且很难看出是格式问题. 测试里只留了 `normalize` —— 那是**对拍特有**的兼容处理
  (两处"记录方式"上的差异), 与格式无关.

- 生成器有两处设计上的选择, 都不是绕路而是必须:

    格式 (那边是个 6.8 KB 的 `profile` 字符串要 `STR_UNPACK`), 引擎造不出来也不该造. 这一份
    直接从真实录像里借 —— 它记的是"这个档解锁了什么", 与种子 / 牌组 / 赌注都无关.
  - **动作只用 `select` / `play` / `discard` / `cash_out` / `next_round`**: 路径最短, 而它验的正是

- 生成器自己验过两层: 生成的文件能被对拍器读回来逐步走通 (格式合法, 动作都能执行), 而且

  与更深的底注. 要让路径变长就得让它会凑顺子 / 同花 (或者会挑目标分数), 那是"写一个会玩的
  bot", 属于另一件事 —— 记在这里, 下一轮再决定要不要做.

- 上一轮那个"策略太弱"的局限这一轮解决了, 而且做法比写启发式干净: **让引擎自己算**.

  按打出来的分挑最好的一手". 好处是它走的是**真计分路径** (牌型, 小丑, 版本, 削弱, 牌背
  效果全在内), 不会因为启发式漏看某个组合而与实际不符; 顺带也算快照 / 回滚这个能力的一个用例.
  整局生成仍然只要一两秒.

- **一个纠正, 而且是我自己先想错的**: 我一直以为"漏掉一次掷骰会让后面**所有**掷骰错开一格",
  并照这个理解写过好些注释与推断. 这次量下来它是**错的** —— 游戏的随机数是**按键独立**的.

  机制在 `pseudorandom` 自己身上: 每次调用都先 `pseudoseed(键)` (只读**这个键**自己的计数
  与开局的种子), 再 `math.randomseed(seed)`, 最后取一个数. 于是任意两个键的序列互不影响:
  先连掷 8 次 `wheel` 再掷 `joker`, 与直接掷 `joker` 拿到的是同一个数.

  实测 (LuaJIT 与本引擎一致, 见 `tests/luajit_parity.rs::random_keys_are_independent`):
  同一份 fixture 里 `after8` 与 `none` 两组**完全相同**就是这个意思.

  结论要按这样理解, 它决定了"漏一次掷骰"的轻重:
  - 漏掉某键的一次掷骰 ⇒ 只有**那个键**之后的取值会错位 (例如"第几张幸运牌");
  - 某个键掷了但结果没人看 ⇒ 对别的键**毫无影响**.

  我把这个当成本轮最重要的一条, 因为它影响三件事: 判断一个缺失分支到底有多严重, 决定要不要
  为它写测试, 以及别把力气花在错的地方. 代码里几处夸大的注释 (说什么"后面所有掷骰都会错开")
  已经按这条改正.

- **补上轮子 (The Wheel) 抽牌那一掷, 但它是个特例: 掷了也看不出来.**
  轮子的规则是"每张抽进手牌的牌有 1/7 概率背面朝上", 写在 `Blind:stay_flipped` 里, 而那一句
  带着 `pseudorandom(pseudoseed('wheel'))` —— 所以**每抽一张牌掷一次**. 引擎原来完全没接.

  为什么它不影响对拍: `'wheel'` 这个键在全游戏里**只在这一处**用到 (按键独立, 所以它不影响
  别的键), 而"背面"只影响画面 —— 它不吃计分, 也不进 digest (`format.lua` 的 `card_token`
  只用 key / 版本 / 蜡封 / 强化 / 永恒 / 租赁, 背面不在其中; `facing` 那边只被精灵与影子读).
  所以这一掷目前**没有任何可观测效果**.

  仍然照掷的理由是忠实: 它是 `stay_flipped` 的一个真实分支, 该像游戏一样往前走. 而正因为
  **回放对拍永远抓不到它**, 验证只能直接对值 —— 加了一份 LuaJIT 对拍 (`dump_rng.lua` 的
  `# wheel` 段) 与一条"发一手牌之后这个键应当推进到第 (牌数 + 1) 次"的接线测试.
  两条都验过鉴别力: 把接线去掉, 接线测试立刻红.

- **本机那个 `luajit` 不能当随机数的数值基准** (这一轮最要紧的一条, 差点让它带偏).
  起因是给幻象券那条路生成对拍数据时, 引擎与 LuaJIT 的数值对不上. 查下去发现不是引擎的错:

  - 引擎实现的是 LuaJIT **v2.1 分支**的 `random_seed`. 这一点可以证明: 把 `lib_math.c` 里那个
    函数原样抄成一份独立实现 (Python), 它能**复现 LuaJIT 自己写在 `lj_prng.h` 里的预计算常量**
    `lj_prng_seed_fixed` —— 那个常量旁边的注释就写着"这是 `random_seed(rs, 0.0)` 的预计算结果".
    抄对了才可能算出那个数.
  - 本机装的 `luajit` 是 2.1.1774896198, 它与 v2.1 的源码在**约 15% 的种子**上给出不同的首个
    `math.random()` (实测 20 个随机种子里 3 个不同). 而 master 分支里 `random_seed` 这个函数
    **已经不存在了** —— 说明新版换过播种算法. 所以本机这个是"另一版", 不是 v2.1.
  - 哪一边与**游戏**一致? 证据在回放: 十九份录像逐步对拍 1447 步全过, 而商店内容依赖大量
    `pseudorandom` 阈值判定 (稀有度 / 版本 / 池子 / 永恒那几项). 若引擎的 PRNG 对 15% 的种子是错的,
    那些判定会大面积跑偏, 不可能 1447 步全中. 所以游戏用的那一版与引擎一致.

  结论: 引擎是对的, **本机 luajit 是错的参照物**. 影响与对策:
  - 以后用本机 `luajit` 生成期望值时, 只能取**与版本无关**的量 —— 计数, 顺序, 或者"这些值是否
    恰好落在两边都同意的那 85% 里".
  - 已经把那条幻象券的对拍测试改成只验**次数** (`illusion` 这个键掷几次), 因为次数是纯计数,
    与播种算法无关, 而"次数"恰好是这段代码最容易写错的地方.
  - 之前几条基于本机 luajit 的对拍 (洗牌, pseudoseed 递推, 轮子那八掷) 都通过, 说明那些具体的值
    落在两边都同意的一侧, 可以留着; 但**不能**因此认为"本机 luajit 永远可信".

- 补上幻象券 (与它的前置"魔法把戏券") 那条商店路径. 三件事原来都没有:

  1. **扑克牌那一格可能是"强化牌"**. 判据在游戏那张权重表的第三项上, 写法很绕:
     `(used_vouchers.v_illusion and pseudorandom(pseudoseed('illusion')) > 0.6) and 'Enhanced' or 'Base'`.
     要害是**这一掷在"这一格是什么类型"定下来之前就发生了** —— Lua 会先把整个 table constructor 求值完
     再交给 `ipairs`, 所以哪怕这一格最后是张小丑, 这一掷也照样花掉. 挪进分支里就是错的顺序.
  2. **强化牌要抽一次 `Enhanced` 池, 基础牌不抽** (游戏里基础牌走 `forced_key = 'c_base'` 那条短路).
  3. **版本那两次掷骰的位置很反直觉**: 它不在 `create_card` 里, 而在调用方拿到牌**之后**,
     判据是"这一格是扑克牌且有幻象券" (超过 0.8 才给, 给了再掷一次决定给哪个版本).

- **买扑克牌那条路原来会直接报错.** 商店里买下的扑克牌进的是**牌堆** (`G.deck:emplace`),
  与小丑 / 消耗牌都不同; 引擎原来只分"消耗牌"与"其余", 于是买扑克牌会被当成小丑去查原型表,
  抛 `UnknownCard`. 而魔法把戏券**开局就是解锁的**, 所以这是"一买就崩"的路 —— 只是十九份录像里
  没人买过. 现在按记号 (`花色_点数`) 判: 这类牌进牌堆, 并且走**同一个入口**喂全息图那个钩子
  (`playing_card_added`), 而不是自己插一遍.

- 顺手修掉一个插入位置的老错: `add_playing_card_to_deck` 原来用 `push` (**牌堆顶**),
  应当是 `insert(0)` (**牌堆底**). 这条语义在别处早就对齐过 (收弃牌回牌堆 / 标准包取出的牌都按它写) ——
  `CardArea:emplace` 对牌堆是特例 (插数组头部), 而抽牌取尾部, 两下一合就是"新加的牌最后才抽到".

  **录像抓不到它**: 十九份录像里大理石 `j_marble` 在**货架上出现过 71 次, 进队 0 次** —— 效果从没触发过.
  两个方向都试过 (`push` 与 `insert(0)`), 对拍都是 19/19 全过, 正是这个原因. 这类分支只能读源码定,
  再由单测钉住: 加了一条断言"新加的牌在下标 0 (牌堆底)", 并且退回成 `push` 确认它会红.

- 这一轮的另一半时间花在**清点覆盖面**: 把游戏里所有 `pseudoseed` 的**字面量键**抽出来 (50 个) 逐个查引擎.
  缺的 5 个里:
  - `edition_deck` —— 没有任何原版牌组带 `edition` 配置, 走不到;
  - `flipped_card` —— 挑战模式专用 (而回放格式本身就拒绝挑战);

  - `illusion` —— **真的缺**, 就是上面那条, 已补.

- 顺着"哪些全局随机数没建模"查下去, 挖到一个**新机制**, 而且它正好落在验收面上 (首个商店的赠包):

  **游戏的 `Card()` 构造函数每造一张牌都无条件消耗 3 颗全局随机数**:

  ```lua
  self.discard_pos = {
      r = 3.6*(math.random()-0.5), x = math.random(), y = math.random()
  }
  ```

  这三颗只用来写牌被丢弃时的动画摆位 (纯视觉), 但它们**推进全局 PRNG 的位置** ——
  于是任何在它之后发生的**全局** `math.random` 取值都会跟着变.

  引擎一处都没建模. 露头的地方就是每局第一个商店白送的那个小丑包 (`get_pack` 的第一次调用):

  ```
  return G.P_CENTERS['p_buffoon_normal_'..(math.random(1, 2))]
  ```

  它读的正是全局位置, 所以取决于"在它之前一共消耗了多少颗".

- 量出来的事实 (做法: 把对拍器里那条豁免去掉, 看哪些录像会红):
  - 十九份录像里**十八份**的编号引擎算得完全正确, 包括那份算出 `_2` 的 LG7RIX92;
  - 只有 XXWF71H9 差一 (引擎 `_2`, 记录 `_1`);
  - 所以差异是真的, 但范围很小.

- 追的过程与结论: 把引擎里"铺货时每一个 `pseudoseed` 的键"打出来, 与**独立复刻的 oracle**
  (见下一条) 对算, 可以确定两件事:
  1. 货架上的**每一张牌**都对 —— 小丑 `j_trading`/`j_rocket`, `j_abstract`/`c_jupiter`,
     券 `v_magic_trick`/`v_planet_merchant`, 第二个包 `p_arcana_normal_4`/`p_celestial_normal_4`
     全都与记录一致. 也就是说**掷骰的种类与顺序是对的**, 只有全局位置偏了.
  2. 第二个包之所以从来不错, 是因为它走的是 `pseudorandom('shop_pack'..底注)` —— **会重新播种**,

  券那一格的数量由 `starting_params.vouchers_in_shop` 控制 (Steamodded 把它设成 1)。

- 接着查"全局随机数到底差几颗" (就是那个白送的小丑包编号). 查清了几条**代码事实**, 但**修失败了**,

  **先说失败**: 我拼出一个模型, 把三份不同种子的录像 (ALEEB / LG7RIX92 / XXWF71H9) 的编号同时对上,

  顶出来. 教训: **任何"把测试放松一点"的改动, 都要先确认放松真的生效** (数一下那个记号还有几个),
  再去跑. 否则看到的就是自己制造出来的通过.

  **代码事实** (这些是查了源码的, 但拼不成一个对得上的模型):

  - `Card:juice_up` 里有一句 `math.random() > 0.5` 决定抖动方向, 每次调用**恰好消耗 1 颗**全局随机数;
    而 `Card:start_materialize()` 会调 `juice_up()` —— 也就是**每张被 materialize 的牌多 1 颗**.
  - `Particles:update` 里有 7 颗 `math.random()` (位移 / 方向 / 大小 / 速度), 但它在 `update` 里 ——
    **每帧**都消耗. 也就是说"数全局随机数"只对**同一帧内**跑完的代码有效; 商店铺货正好是同一帧,
    画面更新插不进来 (这也解释了同种子的多份录像那个编号为什么稳定).
  - `Card:init` 里 `discard_pos` 那三句 (`r` / `x` / `y`) 原版是 3 颗全局随机数, 但本仓库的
    Steamodded 在 `better_calc.toml` 里带了一个把整块换成常量 (`r = 0, x = 0, y = 0`) 的补丁
    (原处还留着一句 `#wtf`). 这个补丁**到底有没有生效**没能确认 (lovely 的 dump 目录不在),
    但它是个陷阱: 照原版源码数会得出 3, 照"补丁生效"数会得出 0, 而两种都跟录像对不上.
  - `Game:main_menu` 里有 `math.randomseed(os.time())`. 无害: 每个 `pseudoseed` 都会**确定性**地
    重新播种, 所以只要在它之后取值, 墙钟那一下就被覆盖了.
  - `fixes.toml` 给 `pseudoseed` 加了一句 `if G.SETTINGS.paused and key ~= 'to_do' then return math.random() end`
    —— 暂停时 `pseudoseed` 改用全局随机数. 回放/录像期间游戏没暂停, 所以这条不影响对拍, 但它说明
